Основание: `AUDIT_BUILDER.md` (аудит по 10 инструментам) + глубокое изучение кода (карта builder 3262 строк, components/, lib/, api/, данные 292 шаблонов).
Статус: план согласован к исполнению.

## 0. Что меняем и почему (резюме)

Продукт функционально силён (правовой аудит, пакет документов с SHA-256, версии черновиков, подписи), но визуально и по UX — MVP: монолитная страница 3262 строки с 36 useState и 12 сворачиваемыми сервисными блоками; нет двухпанельного «анкета + живой предпросмотр» (эталон Doczilla/Комбинатор); сканер без камеры и без локальных worker (хотя файлы уже лежат в `public/workers/`); корзина фейковая (hardcoded); 0 тестов; нет git.

План — 9 фаз + инфраструктура. Принцип: **каждая фаза — деплойбельный инкремент с зелёными тестами**, поведение документов не меняется, данные не теряются.

## 1. Принципы и жёсткие ограничения

1. **Никаких новых runtime-зависимостей.** Все runtime-пакеты (15 шт.: next, react, supabase, tesseract.js, jspdf, html2canvas, pdf-lib, docx, mustache, qrcode, lucide-react и др.) — достаточны. Новое — только devDeps: vitest, @playwright/test, @testing-library/react, jsdom.
2. **Тесты появляются раньше изменений.** Фаза 0 фиксирует текущее поведение e2e-тестами; каждый последующий рефакторинг обязан проходить их.
3. **Инкрементальность.** Не трогаем движок рендера/экспорта в Фазах 1–2 (только UI-композиция); экспорт-улучшения — в отдельной Фазе 6.
4. **Гигиена.** tsc strict (включён) + eslint + `npm run audit:acts` (аудит ссылок на НПА в шаблонах) — зелёные перед каждым деплоем. Деплой: `npx vercel --prod --yes`, проверка `npx vercel ls --prod`.
5. **Безопасность данных (152-ФЗ).** Всё OCR/подписи/черновики — локально в браузере; DADATA-прокси `/api/dadata` только для подписчиков (монетизация PRO) — сохранить, но типизировать.
6. **Не коммитить, не пушить без запроса пользователя** (по правилам сессии); выкладки — только по явной команде.

**Критический факт:** в проекте **нет git-репозитория** (`.git` отсутствует). Долг по Фазе 0: `git init` + baseline-коммит до любых изменений, иначе нет возможности отката и последующего CI.

### ФАЗА 2 — Форма: эргономика полей (M)

**Цель:** правила NN/g (одна колонка, помощь при вводе, честные обязательные поля) — без потери скорости заполнения длинных шаблонов.

1. **Секции вместо табов для длинных шаблонов (>20 полей):** все категории рендерятся последовательно (одна колонка), сверху — sticky-навигация по категориям с прогрессом «✓ N/M» (якорный скролл, active-подсветка). Для ≤20 полей — единый экран без навигации. Табы удаляются (их скрытость контента — главная претензия NN/g; 63-полей ГИБДД при табах теряют контекст).
2. **Placeholder → helpText:** требования формата («17 символов», «4 цифры») переносятся в `label`-подпись или `validation.helpText` (поле в типе уже есть, в UI не выводится — вывести под полем, серый мелкий текст); placeholder остаётся только для примеров значения («25.05.1996»), не для инструкций.
3. **Демо-дефолты:** скрипт-аудит всех 292 шаблонов: `defaultValue` непустые для text/number/date → пустая строка (кроме осознанных: checkbox, select с одним вариантом, «_same=true»); демо-бейдж «Убрать значение» (1496–1521) оставить для checkbox.

### ФАЗА 3 — Сканер документов (M)

**Цель:** честный «офлайн-сканер»: локальные worker (файлы уже в `public/workers/`), камера на мобиле, подтверждение распознанного.

Статус «Загрузка модели (~8 МБ)…» с прогрессом; один worker на вкладку.
2. **Ввод:** две кнопки: «Сфотографировать» (`<input capture="environment">`, мобильные) и «Выбрать файл» (`accept="image/*"`). Передавать тип: `passport | pts | sts` (сейчас обе кнопки зовут один handler без типа — 2084–2104).
3. **Сторона документа:** перед сканом обязательный мини-выбор «Паспорт Продавца/Покупателя» (или «ПТС/СТС») — префикс seller/buyer формируется явно (сейчас ветка существует в коде, но не в UI — 954–957).
4. **Подтверждение:** распознанное показывается карточкой «Что распознано» (ФИО, серия/номер, дата, адрес; для ПТС/СТС — VIN/марка/год) с чекбоксами полей → «Применить к форме» (не вписывать молча). Сохранение распознанного изображения не выполняется (152-ФЗ) — только текст.
5. **Тесты:** фикстуры (сгенерированный паспорт-макет с наложениями) — unit: эвристики по типам; e2e-лайт: загрузка фикстуры → поля применились (worker мокается в тесте, в dev-режиме реальный прогон одного файла).

**Критерий готовности:** сканер не грузит ничего с CDN (network-assert в e2e); распознавание контрольного тестового изображения (обязательно тестовый образец — до 3 попыток исправить эвристику); реальный прогон на телефоне (Android Chrome) — камера работает.
