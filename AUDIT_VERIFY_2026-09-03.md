### 2. `accept` по-прежнему не проверяет владельца документа


### 3. Верификация — имитация, и сообщение стало опаснее

`verify/route.ts:133-136`:
```js
return {
  valid: true,
  byteRangeValid: true,      // ← литерал. ByteRange не читается нигде
  certValid: true,           // ← литерал
  certExpired: false,        // ← литерал
  certExpiringSoon: false,   // ← литерал
};
```

Что `verifyPAdESSignature` реально делает: находит AcroForm → находит поле `/FT /Sig` → читает `/Contents` → проверяет, что это hex длиннее 100 символов → `valid: true`. **Всё.** Ни криптографии, ни ByteRange, ни цепочки сертификатов, ни CRL/OCSP, ни метки времени.

Единственная живая проверка — `if (signingDate > now) certValid = false` (стр. 124) — и её результат никуда не попадает: строка 134 всё равно возвращает `true`.

А ответ пользователю стал **жёстче**, чем был:

> «Подпись валидна: PAdES проверена, ByteRange корректен, хэш совпадает, сертификат действителен»

Все четыре утверждения не обеспечены кодом. «Хэш совпадает» — тавтология (хэш файла сравнивается с хэшем того же файла). Остальные три — константы.

**Подделать такой «проверенный» документ — 10 строк на pdf-lib:** создать поле `/FT /Sig` и положить в `/Contents` 100 любых hex-символов. Эндпоинт ответит «подпись валидна».

По 63-ФЗ это прямая зона ответственности: документ с таким заключением могут показать в суде как доказательство с действительной ЭП.

**Минимум до продакшена:** переименовать `/api/sign/[id]/verify` в `/status`, убрать из ответа всё, что не проверяется, возвращать `byteRangeValid: null` (не проверялось) и писать честно: «Проверена только структура подписи. Криптографическая проверка требует КриптоАРМ/КриптоПро CSP на сервере».
