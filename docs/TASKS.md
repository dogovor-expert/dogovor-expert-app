## 1. Расширение RAG-корпуса AI-юриста (НПА)

**Статус:** открыта · **Приоритет:** средний · **Тип:** данные + прод-БД

**Зачем:** AI-юрист ссылается только на акты, загруженные в `law_chunks`. Сейчас
активны 7 НПА (3908 чанков): ГК ч.1/ч.2, ЖК, ТК, КоАП, ЗоЗПП, СК РФ. Чем шире
корпус, тем чаще ответы получают проверяемые ссылки на действующие редакции.

**Как делать — ПО ОДНОМУ АКТУ ЗА ПРОГОН.** Не дробить один документ между
прогонами и не смешивать с другими задачами: иначе расходится `parser_version`,
ломается completeness-gate и активация уходит в прод частично. Один акт = один
полный цикл. Если нужно много — делаем отдельный выделенный прогон (батч).

### Предусловия

- Тоннель к прод-БД (умирает при длинных прогонах — перезапускать):
  `Start-Process ssh -i ~/.ssh/firstvds_migr -o ServerAliveInterval=30 -N -L 127.0.0.1:55433:172.18.0.6:5432 root@82.146.35.220`
- Секреты (локально, НЕ в git): `pgpass` прод-БД, ключ `PROXYAPI_API_KEY`
  (локальный `.env.local`-ключ мёртв → 401, брать из CapRover env).
- Миграции корпуса уже применены на проде (4 шт., см. `supabase/migrations/20260925_law_corpus*.sql`).

### Runbook (один акт)

1. **Найти ND** документа в официальном IPS `pravo.gov.ru/proxy/ips` по названию;
   зафиксировать `nd`, официальный URL, дату редакции из преамбулы.
2. **Добавить документ** в `LAW_DOCUMENTS` (`src/lib/legal/lawCorpus.ts`):
   `code`, `title`, `nd`, `officialSourceUrl`, `sourceName`, `license`,
   `mustContain` — маркеры статей для completeness-gate (начало и конец текста).
3. **Fetch:** `npx tsx scripts/fetch-law-corpus.mts` → MHTML-архив
   (`?savertf=&nd=...&page=all`), НЕ постраничный `page=1` (он обрезан).
4. **Проверить парсер:** `npx vitest run src/lib/__tests__/lawCorpus.test.ts` (14+ кейсов).
   Добавить кейс на подномера статей нового акта.
5. **Load в draft** через тоннель: `node scripts/run-load-corpus.mjs --dir=<...>`
   (сначала `--dry-run`). Эмбеддинги с retry, идемпотентно.
6. **Верификация:** `scripts/verify-law-corpus.mts` — completeness-gate, drift по
   `source_sha256`, fidelity-выборка дословности; плюс anomaly-scan по меткам статей.
7. **Retrieval-тест:** прогнать контрольные вопросы по новому акту через реальную
   `match_law_chunks` — ожидание не ниже baseline (10/10 на текущем наборе).
8. **Юрпроверка выборки** чанков (редакция, метки, отсутствие мусора) →
   **активация:** `run-load-corpus.mjs --activate --reviewed-by="<кто проверил>"`.
9. **E2E на проде** `/api/ai/chat`: запрос из темы акта → `sources` содержит
   документ с корректной `edition_date` и `source_url`.
10. **Гейты:** `npx tsc --noEmit`, `npx eslint .`, `npx vitest run --exclude="**/__integration__/**"`.
11. Обновить таблицу очереди и «Итоговое состояние корпуса» ниже.

### Критичные нюансы (иначе тихая порча данных)

- **`law_chunks.article` loader НЕ обновляет** (SET chunk/embedding/heading/locator/
  source_url). При смене парсера метки в БД синхронизируются **вручную** по
  `(edition_id, chunk_index)`. Проверять anomaly-scan после каждой смены парсера.
- `content_sha256` считается по тексту, а не по чанкам → смена меток не создаёт
  новую редакцию (переиспользуется существующая). `parser_version` у редакции при
  конфликте не обновляется (только у чанков) — учитывать при аудите версий.
- Редакции со статусом `draft` для RAG невидимы: `match_law_chunks` берёт только
  `status='active'` и `effective_from <= today <= (effective_to|∞)`.
- Ограничения БД: `verified/active` требуют `legal_reviewed_at`; `active` требует
  `effective_from`. Не обходить — это юридические ворота.
- Синонимную таблицу `law_synonyms` (`law_expand_query`) пополнять при появлении
  новых терминов, иначе OR-FTS теряет разговорные формулировки.

### Критерий готовности (DoD)

- Акт загружен, верифицирован, активирован; anomaly-scan = 0.
- Retrieval по теме акта даёт релевантные статьи (не ниже baseline).
- E2E `/api/ai/chat` отдаёт `sources` с этим актом.
- Все гейты зелёные; таблица очереди обновлена.

### Стратегическая задача: Вложения (фото/PDF) + vision

**Статус:** нужно · отдельный осознанный проект (не «между задачами»).

Разбор договоров глазами модели — самая ценная и самая тяжёлая фича. В тарифах уже
заложена цена «разбор документа» и есть `AI_MODEL_VISION`. Перед реализацией
продумать: переиспользование бакета `chat-files` (TTL, whitelist MIME), передача
изображения в модель, учёт vision-себестоимости, лимиты размера/страниц, приватность
(PII в документах), очистка. Сложность — **L**.

### Отклонено (сознательно не делаем)

| Функция | Почему нет |
|---|---|
| PRO-подписка для AI | Баланс + топ-ап честнее для поштучной услуги; подписка — лишний биллинг без выгоды |
| Обратная связь 👍/👎 | Есть виджет поддержки; отдельная таблица/API/модерация избыточны |
| Стриминг ответа (SSE) | Усложняет списание, отмену и ошибки; ответ и так ~10 сек |
| Кликабельные ссылки в PDF/DOCX | Экспорт читают/печатают; правка общего рендера рискованна |
| Голосовой ввод (STT) | Юридический вопрос удобнее текстом; лишняя цена/хранилище/ошибки распознавания |
| Поделиться диалогом | Приватные юрвопросы не шарят; риск утечки PII и лишняя модерация |

Сложность: **S** — до полудня, **M** — 1–3 дня, **L** — неделя+ (миграции/прод/юрпроверка).

### Инварианты (не нарушать)

- Экономия памяти: тяжёлые либы — только ленивым `import()` (как в экспорте). Не грузить pdf-lib/docx в стартовый бандл.
- Список сообщений ограничен 100 (`/api/ai/threads`); при росте — виртуализация, а не увеличение лимита.
- Списание денег — только после успешного ответа; ошибки провайдера не списывают.
- Экспортный HTML обязан иметь **один корневой элемент** (`exportPdf` берёт `body.firstElementChild`).

### Несоответствия копий (исправить текст)

- «Разбор договоров и фото, голосовые и видео — скоро»: голос/видео отклонены — убрать из строки; «разбор документов» появится вместе с задачей vision.
