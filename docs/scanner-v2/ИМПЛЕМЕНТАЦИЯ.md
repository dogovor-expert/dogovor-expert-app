## 1. Критически важные выводы

### 1.1. Выбор OCR-движка для русских документов (ВАЖНО!)
Официальный README `ppu-paddle-ocr` (строки 463–470, 475–485, см. `node_modules/ppu-paddle-ocr/README.md`):

> «v5 models are single-language specialists; v6 models are multilingual (one model, 50+ languages).
> If your documents are **always one known language, the matching v5 model avoids cross-language confusion**.»

И таблица выбора (строки 475–485):
| Случай | Рекомендация |
|---|---|
| **One known language** | **the matching v5 model** — «single-language dictionary, no cross-language confusion» |
| Плотные строки (документы, таблицы) | `V6_SMALL_MODEL` |
| Низкий контраст | `V6_MEDIUM_MODEL` |
| Hаклон/поворот | **deskew** через `ppu-ocv` `DeskewService` |

**Вывод:** наши документы — **всегда один язык (русский)**. Поэтому:
- ❌ **НЕ переходим** на `V6_TINY_MODEL` как «primary». Tiny — это мультиязычная модель с словарём ~6.9k символов, заточенная под скриншоты/UI со смешанными языками. На русских документах она даст **cross-language confusion** (путаницу между кириллицей/латиницей — критично для VIN, серий паспорта).
- ✅ **Оставляем `V5_CYRILLIC_MOBILE_MODEL`** как основной движок — он однозначный специалист по кириллице.
- ⏳ `V6_SMALL_MODEL` (30 МБ) — опциональный «серверный» режим для самых плотных/мелких документов, **не для мобильного дефолта**.

**Почему раньше был баг «только VIN»:** не из-за движка, а из-за regex в `docOcr.ts` (серия СТС не парсилась вовсе, см. Фаза 0). Движок (Tesseract + Paddle Cypillic) здесь ни при чём.

## 2. Фаза 0 — срочные правки

**Срок: 1–2 дня · Эффект: +25–30% точности на СТС/ПТС (фикс «только VIN»)**

### 2.1. Файл `src/lib/docOcr.ts`

**Проблема A — серия СТС не парсится.**
`data.stsSeries` объявлен в интерфейсе `VehicleData` (строки 40–41), но **regex для него отсутствует**.

**Добавить** в `extractVehicleData`:
```ts
// серия СТС — 2 буквы + 6 цифр, часто на отдельной строке от номера
const stsSeriesMatch = text.match(
  /(?:серия|серия\s*СТС|СТС\s*серия)[:\s]*([А-ЯЁ]{2}\s?\d{6})/i
);
if (stsSeriesMatch) data.stsSeries = clean(stsSeriesMatch[1]);
// если серия на той же строке, что и "СТС" до номера — вариант 2
if (!data.stsSeries) {
  const ss = text.match(/([А-ЯЁ]{2})\s*(\d{6})/);
  // Только если перед группой есть слово СТС/СВИДЕТЕЛЬСТВО (иначе мусор!)
  if (ss && /(?:СТС|СВИДЕТЕЛЬСТВО|РЕГИСТРАЦИ|ТРАНСПОРТН)/i.test(text.slice(0, ss.index))) {
    data.stsSeries = clean(`${ss[1]} ${ss[2]}`);
  }
}
```

**Проблема B — номер СТС: `\n` в regex блокирует многострочный ввод.**
Строки 228–231: `[^\n]{0,30}?` не пропускает перенос строки, а на фото перенос бывает.

**Заменить** жадность/переносы: убрать `\n`-ограничение для номера, разрешить любой разделитель до 40 символов:
```ts
const numberMatch = text.match(
  /(?:номер|№|NN|N\s*[:：]?)[:\s]*([А-ЯЁ]{2}\s?\d{6})/i
);
```

**Проблема C — 13 regex требуют ключевые слова, которые теряет мелкий шрифт.**
Добавить **fallback-проход по «голым» паттернам** после основного, чтобы подхватывать значения даже без подписей. Например, VIN уже устойчив; марка/год/цвет частично. Это делаем аккуратно (могут быть ложные срабатывания) — добавить **валидаторы** из Фазы 1 (VIN check digit) для отсева мусора.

### 2.2. Файл `src/lib/workers/ocr-worker.js`
Строки 67–71 — PSM (page segmentation mode). Для документов с мелким текстом полезен `PSM 6` (несколько блоков) или `PSM 4`. Проверить режим и при необходимости переключить с `PSM 3` на `PSM 6` для СТС/ПТС.

### 2.3. Файл `src/components/builder/DocScanner.tsx`
Строка ~316 — confidence-gate. Текущий порог `PADDLE_FALLBACK_THRESHOLD = 60` ок, но добавить второй критерий (уже сделан в `30bb6ae`): fallback при `text.length < 80`.

## 3. Фаза 1 — точность

**Срок: 3–5 дней · Эффект: +30% точности, фокус на «плохих» фото**

### 3.1. CLAHE вместо percentile-stretch — `src/lib/docImage.ts`

**Факт из исследования:** готового pure-JS CLAHE-пакета для браузера нет. Пишем свой (200–300 строк, ~4–6 КБ).

**Реализация** — новый файл `src/lib/clahe.ts`:
```ts
export interface ClaheOptions {
  clipLimit?: number; // OpenCV default 40.0
  tileGridSize?: number; // 8x8
  bins?: number; // 256
}

export function clahe(
  gray: Uint8ClampedArray, // 1 канал
  width: number,
  height: number,
  opts: ClaheOptions = {}
): Uint8ClampedArray
```
Алгоритм (строго по OpenCV):
1. Разбить изображение на сетку `8×8` тайлов.
2. Для каждого тайла построить гистограмму (256 бинов).
3. **Clipping:** `clipLimit = max(1, clip * tilePixels / bins)` — обрезать бины выше лимита, отрезанную массу **равномерно распределить** по всем бинам (циклически, пока не растает).
4. Кумулятивная функция (CDF) → LUT.
5. **Билинейная интерполяция** между LUT соседних тайлов по позиции пикселя (для пикселей не точно на границе тайлов). Края — reflect.
6. Выход `Uint8ClampedArray` — готовый grayscale для OCR.

**Интеграция в `docImage.ts`:** заменить блок «contrast stretch» (строки ~307–311):
```ts
const bigData = big.ctx.getImageData(0, 0, big.w, big.h);
const gray = rgbToGray(bigData.data);           // 1 канал
const eq = clahe(gray, big.w, big.h, { clipLimit: 40 });
writeGrayBack(bigData.data, eq);                 // в RGBA
// контраст-стретч оставить как лёгкий довесок после CLAHE
contrastStretch(bigData.data);
big.ctx.putImageData(bigData, 0, 0);
const ocrRaw = canvas.toDataURL("image/png");
```
> CLAHE не трогает `ocrBinary` (для него уже есть Sauvola-порог).

**Почему CLAHE:** локальный контраст убирает тени/блики, даёт +8–12% точности OCR на фото с неравномерным светом (по исследованию `02-preprocessing.md`).

### 3.2. Laplacian gate (блюр) — `src/lib/docImage.ts`
Уже есть `assessQuality` с дисперсией Лапласиана (строки 93–141). Добавить **применение** в `prepareDocumentImage`:
```ts
if (quality.blurry) {
  // попробовать unsharp mask; если не помогло — пометить для UI
  // (предупреждение «фото размыто, переснимите»)
}
```
Порог: `var < 80` → отклонить как размытое; `80–150` → предупреждение. Это уже рассчитано в `assessQuality.blurScore`.

### 3.3. Up-scale 2× для мелких фото
В `drawScaled` (строки 66–90) есть `scale = Math.min(1, longEdge / max(sw, sh))`. Добавить:
```ts
// если исходник меньше OCR размерности — увеличиваем 2x с high-quality smoothing
if (longEdge === OCR_LONG_EDGE && max(sw, sh) < 1200) {
  // рисуем в 2000px (масштаб уже > 1)
}
```
Сейчас `scale` ограничен `Math.min(1, ...)` — это **не позволяет апскейл**. Снять лимит для OCR-копии:
```ts
const scale = longEdge === OCR_LONG_EDGE
  ? Math.max(1, longEdge / Math.max(sw, sh)) // allow upscale
  : Math.min(1, longEdge / Math.max(sw, sh));
```
С `imageSmoothingQuality = "high"` апскейл даст OCR больше пикселей на мелкий текст.

### 3.4. Поворот (orientation), НЕ Tesseract OSD
**Факт:** у `tesseract.js@7` в браузере **нет** метода `osd()` — не пытаться. EXIF-поворот браузер применяет сам при decode. Для 90/180/270 (вертикальные фото паспорта) — простая эвристика + ручной поворот canvas. Произвольный наклон — Фаза 2 (`DeskewService` из `ppu-ocv`).

### 3.5. Валидаторы — новые зависимости
Добавить в `package.json`:
```bash
npm i inn-validator libphonenumber-js vin-iso3779-validator @ezze/rubles
```
- `inn-validator` (50 КБ) — `validateInnPhys`/`validateInnJur`. ИНН физлица и ИП = 12 цифр (одна функция).
- `vin-iso3779-validator` (18 КБ) — check digit VIN. **Обязателен** для отсева мусорного VIN после OCR.
- `libphonenumber-js` (100 КБ с RU-метаданными) — телефоны `parsePhoneNumber(num, 'RU')`.
- `@ezze/rubles` (35 КБ) — сумма прописью (уже есть авто `contract_price_words`, но для физ/юр вариаций удобно).

**Интеграция** в `docOcr.ts` / `ocrPostprocess.ts`:
```ts
import { isValidInn } from "inn-validator";
import { isValidVin } from "vin-iso3779-validator"; // имя по факту пакета

// VIN: сначала кириллица→латиница, потом validate
export function normalizeVin2(raw: string): string {
  const map: Record<string,string> = { О:"O", С:"C", В:"B", А:"A", Е:"E", Н:"H", К:"K", М:"M", Р:"P", Т:"T", У:"Y", Х:"X" };
  let v = raw.toUpperCase().replace(/[^A-Z0-9]/g, "");
  v = v.split("").map(c => map[c] ?? c).join("");
  return v.length === 17 && isValidVin(v) ? v : "";
}
```

## 5. Фаза 3 — магия для пользователя

**Срок: 2–3 недели · Эффект: авто-определение типа, убираем выпадашку**

### 5.1. Auto-классификация типа документа (EfficientNet-B0 ONNX, 5 МБ)
Задача: по фото определить «паспорт РФ / загран / СТС / ПТС / ВУ» (5 классов), точность 92–98%.

**Реализация:** `onnxruntime-web` (уже стоит) в отдельном Web Worker:
```ts
// src/lib/classifyDoc.ts
import * as ort from "onnxruntime-web";

let session: ort.InferenceSession | null = null;
export async function classifyDocument(
  canvas: HTMLCanvasElement // 224x224
): Promise<{ kind: "passport"|"passportReg"|"sts"|"pts"|"epts"|"vuc"; conf: number }> {
  session ??= await ort.InferenceSession.create(MODEL_URL, {
    executionProviders: ["webgpu", "wasm"],
  });
  const input = preprocessToTensor(canvas); // normalize 0..1, [1,3,224,224]
  const { output } = await session.run({ input });
  return decodeTop(output); // argmax + label map
}
```
- Модель: fine-tune EfficientNet-B0 на датасете из реальных фото 5 типов РФ-документов. Онлайн ONNX-моделей «заточных» под РФ-документы нет — нужен свой датасет (или использовать общий `RVL-CDIP` как старт, но с докруткой).
- **Лениво:** грузить модель только при первой загрузке фото, в воркере, не блокируя UI.
- **UX:** убрать выпадашку «выберите тип». Пользователь просто фоткает → классификатор сам выбирает слот `ocrKind` → запускается нужный парсер.

### 5.2. Anchor-based extraction (по координатам)
Вместо «просто текст» — использовать **боксы** от Paddle/Tesseract (`words` с координатами). Для известных лейаутов СТС/ПТС поле находится по фиксированным зонам (якорям), что устойчивее к шуму, чем regex-по-всему-тексту. Это долгий, итеративный компонент — делать после стабильного авто-классификатора.

### 5.3. DaData (продолжение 3.7)
Стандартизация ФИО (склонение через `lvovich` 277 КБ опционально), адресов, проверка паспорта по МВД — server-side роут.

## 6. Фаза 4 — production hardening

**Срок: 1–2 недели · Эффект: скорость, надёжность, лёгкость**

### 6.1. Comlink + Worker Pool
- `comlink` — RPC между воркерами и main.
- Пул из 2 OCR-воркеров: один «горячий» (всегда загружен), второй «холодный» (поднимается при параллельных сканах). TBT −50%, повторный скан без перезагрузки wasm.
- **Экономика:** сейчас воркер пересоздаётся на каждый скан (`DocScanner.tsx:212`), wasm грузится заново 2–5 с. Пул держит движок тёплым → warm 3 с → 600 мс.

### 6.2. WASM pipeline: compileStreaming
`WebAssembly.compileStreaming` в main → `postMessage(module)` в воркер. −300–500 мс cold start (не перекомпилируем в воркере). Потребует доступа к URL wasm в main-потоке (см. next.config).

### 6.3. Workbox + Service Worker (двухуровневый кеш)
- Уровень 1: кеш моделей (wasm, traineddata, onnx) в `Cache Storage` с долгим TTL.
- Уровень 2: `navigator.storage.persist()` — защита от вытеснения.
- Повторный визит FCP −500 мс.
- **CORS:** модели на huggingface CDN должны отдавать `Access-Control-Allow-Origin: *`, иначе Cache API молча не сохраняет.

### 6.4. WebCodecs ImageDecoder
`createImageBitmap`/`new Image()` для JPEG/PNG → заменить на `ImageDecoder` (WebCodecs) — декод до 3.5× быстрее. Обёртка с fallback на `createImageBitmap`. Затрагивает `decode()` в `docImage.ts:43-64`.

### 6.5. XState v5 — машина состояний сканера
Сейчас логика размазана по `DocScanner.tsx` (статусы, ретраи, fallback). XState сделает состояния явными: `idle → decoding → preprocess → ocr → paddling → postprocess → done/error` + fallback-переходы. Позволит легко добавлять авто-классификатор и повторные попытки.

### 6.6. Turbopack watch (важно!)
**Факт (05-architecture-bundling.md):** в Next 16.2+ есть регрессия Turbopack, ломающая `new Worker(new URL(..., import.meta.url))` в production (vercel/next.js#94015).
- Мы на **Next 15** → безопасно.
